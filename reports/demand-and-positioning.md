# 수요와 제품 방향

현재 판단은 **문제의 존재는 확인됐지만, 새 제품으로 옮겨 올 수요와 규모는 미검증**이다. 큰 gateway 시장과 좁은 “로컬 quota 최적화” 시장을 같은 것으로 보지 않는다.

전체 지표의 정확한 조회 시각은 [GitHub 스냅샷](../evidence/github-metadata.json)에 있다. 비교 저장소의 stars를 우리 프로젝트의 예상 성장률로 환산하지 않는다.

## 첫 사용자를 좁힌다

추천 대상은 **PC 하나에서 4~16개 coding agent를 쓰며 하나의 사내 API quota를 공유하는 개발자**다. 클라이언트의 base URL은 바꿀 수 있지만 사내 inference engine 설정은 바꾸기 어렵다. 체감 문제는 429 자체보다 재시도·대기·작업 실패와 짧은 질문의 지연이다.

CPU/작은 GPU로 여러 로컬 모델을 실행하는 사용자는 두 번째 대상이다. 이 환경은 quota token이 아니라 slot-time·메모리·context 길이가 병목이므로 같은 점수 하나로 두 환경을 최적화한다고 홍보하지 않는다.

## 제품 접근법 비교

| 접근 | 장점 | 비용·약점 |
|---|---|---|
| 기존 gateway를 설정하고 작은 extension 제공 | 가장 빠르게 실제 수요를 검증. 기능 중복 최소 | 설치·원문 전달·OS 의존성이 기존 제품에 묶임 |
| **Rust 로컬 admission gateway** | 여러 도구에 공통 quota·fair queue 제공. 좁은 핵심을 네이티브로 배포 | 기존 큐보다 낫다는 benchmark와 도구별 호환 검증을 직접 해야 함 |
| 추론 엔진 scheduler/adapter 개발 | token 단위 선점·KV locality에 직접 접근 | 사내 API와 맞지 않고 GPU/엔진별 지원 비용이 큼 |

두 번째를 추천한다. 다만 첫 번째와 비교해 유의미한 이득이 없으면 standalone 구현 이유부터 재검토한다. 엔진 연구는 별도 단계로 남긴다.

## 채택을 확인할 실험

아래 숫자는 시장 예측이 아니라 초기 의사결정용 제안이다.

1. 공개 fixture로 429 burst, 긴 요청과 짧은 요청 혼합, 취소를 한 명령에 재현한다. raw 결과·설정·실패를 함께 공개할 수 있게 준비한다.
2. 별도 승인 후 커뮤니티의 실제 사용자 5명에게 설치·문제 재현을 부탁한다. 지금 외부 메시지는 보내지 않았다.
3. 적어도 3명이 실제 환경에서 2주 이상 반복 사용하고 개선·불편을 설명할 때 다음 기능 투자 여부를 결정한다. 자동 telemetry를 강제하지 않는다.
4. 사내 구두 피드백은 시나리오·도구 버전·동시 agent 수·전후 증상·미확인 항목으로 기록한다. 원문이나 artifact를 반출하도록 요구하지 않는다.

초기 질문은 “이 기능이 멋진가”가 아니라 “지난주에 이 문제로 작업이 몇 번 멈췄는가, 현재 우회법은 무엇인가, base URL 변경과 네이티브 실행이 가능한가, 이 도구를 계속 쓰는가”다.

## 5,000 stars와 Codex for OSS

5,000 stars는 사용자의 장기 목표로 유지한다. 다만 [공식 신청서](https://openai.com/ko-KR/form/codex-for-oss/)에는 5,000 stars라는 최소 기준이 명시돼 있지 않다. 공개 repo와 maintainer/핵심 기여 역할, stars·다운로드·생태계 중요성 등을 설명하게 돼 있다. 숫자를 채운 뒤만 신청할 수 있다고 생각할 필요는 없다.

지원 가능성을 위해 쌓을 것은 재현 가능한 개선 결과, 지속적인 유지보수, 다른 도구와의 실제 호환, 사용자 사례와 기여다. 현재는 새 공개 제품·사용자 채택·지원 자격을 입증할 자료가 없고 신청도 하지 않았다. stars 구매, 과장한 benchmark, 무차별 홍보로 이를 대신하지 않는다.
