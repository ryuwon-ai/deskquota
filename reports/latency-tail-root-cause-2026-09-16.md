# 40.63초 p95의 원인 분석

2026-09-16. 9월 15일의 `quarter_actual` 원시 기록을 요청 ID와 monotonic timestamp로 재계산했다. **새 HTTP 실험이나 성능 개선 결과가 아니다.** 당시 DeskQuota는 `687a5ce`, 기본 RR/actual, cache/retry off였으며 공통 mock은 rolling 60초 RPM16 / 합성 TPM6000 / 동시 실행2였다.

결론은 세 가지다. **성공 집합이 달라 수치 격차가 크게 보이고, 우리 두 요청에는 실제로 약 38초의 전송 전 대기가 있으며, 그 대기에는 피할 수 있는 과대 예약과 같은 root FIFO의 영향도 있다.** 이전 설명에서 RPM만 원인으로 든 것은 불완전했다. 서로 다른 root 사이의 starvation barrier만을 원인으로 보는 것도 틀리다. 두 요청은 모두 root0에 있다.

## 직접 재계산한 시간

시각은 측정 시작을 0초로 잡았다. `전송 전`은 client 제출부터 mock 수신까지이므로 순수 큐 대기 계측값은 아니며 transport도 포함한다. `전송 후` 역시 mock 실행과 응답 전달을 포함한다.

| 요청 | 제출 | mock 수신 | client 완료 | 전송 전 | 전송 후 | 전체 응답 시간 |
|---|---:|---:|---:|---:|---:|---:|
| g0, 큰 입력, root0 | 29.569초 | 67.338초 | 69.841초 | 37.768초 | 2.503초 | 40.272초 |
| g16, 작은 입력, root0 | 31.710초 | 69.841초 | 72.344초 | 38.131초 | 2.503초 | 40.634초 |

두 요청의 mock service 설정은 모두 2.5초다. 입력 길이의 구분과 생성 시간의 구분은 다르다. 첫 16건은 28.727초 이전에 모두 끝났다. 따라서 g0/g16이 기다리기 시작할 때 upstream 실행 슬롯2개는 모두 비어 있었다. DeskQuota의 upstream 시도18회는 전부 성공했고 429·retry는0회였다. 모델 생성이40초 걸렸거나 429 재시도가 누적된 사례가 아니다.

## 코드와 기록으로 재구성한 대기 원인

**아래 장부 값은 기록된 mock 수신/클라이언트 완료 시각을 내부 start/finish의 근사 경계로 사용하는 재구성이다.** 원래 HTTP 실험에 요청별 admission 내부 trace는 없으며, millisecond 미만 내부 순서를 직접 관측했다고 주장하지 않는다. 초 단위 지연과 quota 부등식은 일치한다.

| 시점 | 재구성한 상태 | 막힌 이유 |
|---|---|---|
| 31.710초 | RPM16/16, TPM4297/6000, 실행0/2 | RPM 소진. 완료해도 RPM은 즉시 환급되지 않음 |
| 62.258초 | 첫 RPM 만료, RPM15/16, TPM 잔량1815, 실행0/2 | g0 예약2057이 잔량보다242 큼. g16 예약446은 들어갈 수 있지만 같은 root의 g0 뒤에 있어 검사 대상이 아님 |
| 67.336초 | 두 번째 RPM/TPM 만료, TPM 잔량2103 | g0가 들어갈 수 있음. 실제 mock 수신67.338초 |
| 67.338초 직후 | g0 예약2057 차감, TPM 잔량46, 실행1/2 | g16 예약446이 들어가지 못함. 빈 실행 슬롯만으로 해결되지 않음 |
| 69.841초 | g0 완료 usage515로 정산, 중간 만료까지 반영한 TPM 잔량1700 | g16이 들어갈 수 있음. 실제 mock 수신69.841초 |

관련 코드:

- `product/src/admission/quota.rs`: `WINDOW=60초`, `start()`가 RPM/TPM 만료를 정하고 `check()`가 동시성·RPM·TPM을 함께 검사한다. `finish()`의 actual 정산은 완료 후에만 예약을 보정한다.
- `product/src/protocol/request.rs`: known TPM의 입장 비용은 **JSON 전체 UTF-8 bytes + 출력 상한**이다. 실제 입력 토큰 수가 아니다.
- `product/src/admission/queue.rs`: 각 root의 `front()`만 검사한다. 따라서 g0 뒤의 g16은 자원상 들어갈 수 있어도 앞지르지 못한다. 실험용 backfill도 다른 root의 head만 찾으므로 이 같은-root 사례를 해결하지 못한다.

현재 HEAD와 측정 commit `687a5ce`의 위3파일 차이도 확인했다. 추가 진단·검사 및 상태 설명 변경은 있으나 이 비용식, 입장 결정, FIFO, 만료·정산 규칙은 그대로다. 이는 원인 코드가 남아 있다는 근거이며 현재 바이너리의 latency 재측정은 아니다.

## Bifrost·LiteLLM이2.5초로 보인 이유

| 해당 요청 | Bifrost | LiteLLM |
|---|---:|---:|
| g0 | 2.047ms 뒤429, upstream 시도0 | 14.477ms 뒤429, upstream 시도0 |
| g16 | 2.308ms 뒤429, upstream 시도0 | 14.378ms 뒤429, upstream 시도0 |

경쟁 제품의2.51/2.52초 p95는 **이 두 요청이 빠진 성공 집합**의 값이다. 우리40.63초에는 두 요청이 포함된다. 본 실험에서는 gateway/client retry를 모두 껐으므로 경쟁 제품이 재시도해 두 요청을 완료하는 시간은 측정하지 않았다. 다른 제품의 대기·재시도 설정 전체를 대표하지 않는다.

성공 표본18개에서 nearest-rank p95는 `ceil(18×0.95)=18`번째, 즉 최댓값이다. Bifrost16개, LiteLLM15개에서도 p95는 최댓값이다. 계산 오류는 아니지만 매우 작은 표본의 max끼리, 서로 다른 성공 집합을 비교한 표다.

| 같은 성공 요청 ID끼리 비교 | DeskQuota p95 | 상대 p95 |
|---|---:|---:|
| Bifrost와 공통16건 | 2.775초 | 2.511초 |
| LiteLLM과 공통15건 | 2.775초 | 2.522초 |

공통 집합에서도 우리는 느렸다. g11이 제출21.407초부터 g9 완료 직후인21.680초까지 약273ms 전송 전 지연을 겪었다. 이때 g9의 예약2762가 actual691보다 컸다. 같은 코드·기록으로 재구성하면 TPM 잔량336에 g11 예약446이 들어가지 못한다. g9 완료 정산 후 g11이 시작한 시간과 일치한다. 이 손해를 성공 집합 차이로 설명해 없앨 수는 없다.

## 줄일 수 있는 부분과 남는 부분

**계산상 대조이며 제품 구현·실험 결과가 아니다:** 첫16건의 관측 start/usage와 FIFO를 유지하고, 마지막 두 건의 입력 비용만 fixture의 정확한 입력 단위로 바꾼다. 출력 상한은 낮추지 않는다. 새로운 지연은 mock service2.5초만 포함하며 transport는 생략한다.

- g0 예약: `1993 bytes + 64 = 2057` → `499 입력 단위 + 64 = 563`.
- g16 예약: `190 bytes + 256 = 446` → `48 입력 단위 + 256 = 304`.
- g0는 첫 RPM 만료62.258초에 시작,64.758초 완료 → 응답 시간 약35.188초.
- g16은 두 번째 RPM 만료67.336초에 시작,69.836초 완료 → 응답 시간 약38.126초.
- 이 대조의 p95는 **40.634초 → 약38.126초**, 약2.509초 차이다. g0 자체는 약5.08초 빨라지지만, 이를 전체 p95 감소량으로 더하면 안 된다.

즉, **이 조건의 과대 예약을 제거해도18건 모두를2.5초 p95로 완료할 수는 없다.** RPM16인 한 bucket에 약30초 간격 안으로18건을 제출했기 때문에 일부 요청은 다음 RPM 자리까지 기다려야 한다. 이 계산은 입력을 항상 정확히 알 수 있다는 제품 보장도, 실제 provider의 tokenizer·한도 계약 검증도 아니다. `bytes/4`를 공통 정책으로 바꾸라는 근거가 아니다.

## 다음 조치

1. 완료 응답의2.5초와 즉시 거절을 섞어 성능 순위를 만들지 않는다. 같은 논리 작업18건에 동일 deadline/재시도 예산을 주고 전체 완료 시간, 기한 내 완료율, 성공 지연, 실패를 함께 비교한다.
2. 코드 개선 후보는 먼저 **입장 전 입력 비용 추정**이다. actual 정산은 이미 있지만 입장 전 과대 예약을 해소하지 못한다. 원문·출력 상한을 바꾸지 않으면서 제공자 제한 계약에 맞는 비용을 얻어야 한다.
3. 같은 root FIFO는 별도 정책 문제다. 순서 보존을 무조건 없애거나 다른 root의 backfill을 켜서 해결했다고 주장하지 않는다. 독립 요청의 지연 이득과 앞선 요청 손해를 함께 검증해야 한다.
