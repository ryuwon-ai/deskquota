## HiveMind: 직접적인 선행 작업

[arXiv 2604.17111v1](https://arxiv.org/abs/2604.17111v1)은 2026-04-18 공개된 *HiveMind: OS-Inspired Scheduling for Concurrent LLM Agent Workloads*다. [본문 결론](https://arxiv.org/html/2604.17111v1#S8)이 실제로 `jayluxferro/hivemind`를 연결한다. **OS식 동시 에이전트 스케줄링·로컬 HTTP proxy라는 큰 발상은 이미 존재한다.** 확인한 arXiv 페이지에는 학회·저널 게재 정보가 없으므로 동료심사 논문이나 검증된 성능 결과로 승격하지 않는다. 본문의 주요 평가는 mock agent/API이며, 재시도 유무가 큰 차이를 만든다. 저자들이 cloud API 규모 검증을 후속 과제로 명시한다. 저자의 수치는 우리 성능 수치가 아니고, 이 checkout이 논문 실험 당시 버전이라는 근거도 없다. [평가와 한계](https://arxiv.org/html/2604.17111v1#S5), [Discussion](https://arxiv.org/html/2604.17111v1#S7).

- **로컬 의존성:** Python ≥3.11, httpx/Starlette/Uvicorn/MCP/psycopg 등이 기본 dependency다. Redis와 tiktoken은 별도 extra다. Docker/WSL 필수 구조는 아니다. [manifest L10–55](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/pyproject.toml#L10-L55)
- **PostgreSQL은 실행 경로를 구분해야 한다.** `hivemind proxy`는 core Database를 생성하지 않고 telemetry 연결 실패를 삼키는 경로다. 그러나 CLI는 DSN이 없으면 로컬 Postgres DSN을 자동 선택하여 연결을 시도한다. 따라서 “DB를 전혀 시도하지 않는 기본 proxy”는 아니다. `hivemind`/`serve`의 MCP 경로는 `await self.db.connect()`가 있다. **standalone telemetry의 fail-open을 전체 서비스 DB 무의존으로 설명하면 틀린다.** 실제 DB 미설치 부팅 시간은 미측정이다. [proxy 생성](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/server.py#L492-L540), [CLI DSN 기본값](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/cli_args.py#L279-L285), [startup 연결](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/server.py#L225-L242), [실패 처리](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/telemetry/ledger.py#L250-L257), [명령 분기](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/__main__.py#L91-L105), [MCP 시작](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/server.py#L547-L551)
- **RPM/TPM 범위:** 기본값은 `per_agent`. 전체 합산 사용이 provider limit를 넘은 뒤 각 bucket 한도를 비례 축소한다. 이는 **합산 hard cap의 사전 예약**과 다른 정책이다. 엄격한 공유 RPM 비교에는 별도 `global` 모드를 구분해야 한다. header/Retry-After의 pause는 공통이다. 세션 식별도 explicit ID → body hint → credential/User-Agent hash로 달라지므로 “agent 수”와 “실제 bucket 수”를 같다고 가정하면 안 된다. [기본 scope](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/storage/models.py#L198-L220), [governor 계산](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/scheduler/rate_limiter.py#L317-L353), [공통 header 상태](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/scheduler/rate_limiter.py#L372-L419), [bucket 식별](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/identity.py#L95-L118)
- **TPM·대기 소유권:** SSE 사용량은 정상 완료 뒤 기록한다. 먼저 admission slot을 잡고 내부에서 rate wait/retry를 수행한다. 우리 joint reservation과 비교할 때 입장 전 추정·완료 후 정산, 그리고 quota 대기 중 slot 점유를 분리해야 한다. 어떤 방식이 빠른지는 미측정이다. [완료 후 TPM 기록](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/interceptor.py#L565-L581), [slot 선점과 해제](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/interceptor.py#L227-L247), [slot 내부 rate wait](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/interceptor.py#L645-L673)
- **재시도·스트림:** 기본 추가 재시도 3회, Retry-After가 120초보다 크면 그대로 반환한다. SSE는 전체 EOF를 기다리지 않고 chunk를 전달하고, 이미 전송한 뒤 오류는 재시작 대신 error frame을 만든다. 다만 upstream reader와 downstream 사이 `asyncio.Queue()`에는 maxsize가 없다. **추론:** 느린 소비자에게 미전송 chunk가 쌓일 수 있으므로 “무버퍼/유한 메모리” 보장과는 다르다. 읽은 전달 경로는 원본 body를 넘기며 자동 context pruning 경로는 확인되지 않았다. [재시도 정책](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/retry.py#L64-L105), [SSE retry 경계](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/interceptor.py#L384-L439), [reader queue](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/streaming.py#L143-L172), [chunk 전달·오류 처리](https://github.com/jayluxferro/hivemind/blob/0468db5db9d0526e326b4db26971642301d7deed/src/hivemind/proxy/interceptor.py#L504-L563)

## Tiger-sudo894/NVIDIA-req-limit-proxy

- Python 표준 라이브러리만 쓰는 native script다. 프로세스 공통 `60/RPM` 시작 간격과 client semaphore를 사용한다. 기본값은 **30 RPM·client slot 4개**다. TPM 예약·agent별 공정 큐는 해당 전달 경로에 없다. retry도 같은 StartGate를 지난다. [imports](https://github.com/Tiger-sudo894/NVIDIA-req-limit-proxy/blob/a200efb6d81c66b7f75764d9fe7c7739c74bb47b/nvidia_rate_limit_proxy.py#L1-L15), [시작 간격](https://github.com/Tiger-sudo894/NVIDIA-req-limit-proxy/blob/a200efb6d81c66b7f75764d9fe7c7739c74bb47b/nvidia_rate_limit_proxy.py#L37-L49), [client slot](https://github.com/Tiger-sudo894/NVIDIA-req-limit-proxy/blob/a200efb6d81c66b7f75764d9fe7c7739c74bb47b/nvidia_rate_limit_proxy.py#L65-L97), [CLI 기본값](https://github.com/Tiger-sudo894/NVIDIA-req-limit-proxy/blob/a200efb6d81c66b7f75764d9fe7c7739c74bb47b/nvidia_rate_limit_proxy.py#L253-L272)
- 모든 HTTP 429를 긴 재시도 대상으로 분류한다. 기본 **추가 35회·회당 최소 300초**, 일반 오류는 추가 5회다. 하지만 429를 발견한 thread가 sleep할 뿐 공유 cooldown 시각을 세팅하지 않는다. **“global rate-limit 분류”와 “모든 요청의 공통 cooldown”은 다르다.** 대기하는 client slot도 유지한다. [429 처리](https://github.com/Tiger-sudo894/NVIDIA-req-limit-proxy/blob/a200efb6d81c66b7f75764d9fe7c7739c74bb47b/nvidia_rate_limit_proxy.py#L151-L189), [slot 소유권](https://github.com/Tiger-sudo894/NVIDIA-req-limit-proxy/blob/a200efb6d81c66b7f75764d9fe7c7739c74bb47b/nvidia_rate_limit_proxy.py#L65-L97)
- **성공 SSE도 EOF까지 `SpooledTemporaryFile`에 모은 다음 header/body를 보낸다.** 8MiB는 총 크기 제한이 아니라 메모리에서 디스크로 넘어가는 임계값이다. HTTP 200 내부 worker-exhaustion 문자열을 발견하면 전체 재시도를 할 수 있는 대신, **추론상 첫 토큰 전달은 upstream 전체 완료를 기다린다.** 우리 streaming TTFT 비교에서 이 설계 차이를 숨기면 안 된다. [수집·재시도·전달 L191–240](https://github.com/Tiger-sudo894/NVIDIA-req-limit-proxy/blob/a200efb6d81c66b7f75764d9fe7c7739c74bb47b/nvidia_rate_limit_proxy.py#L191-L240)
- 요청 body는 그대로 전달한다. 읽은 코드에서 context pruning은 없다. 네트워크 시도마다 새 HTTPSConnection을 만드는 구조도 latency 비교에 포함할 조건이다. [원본 body·연결 생성](https://github.com/Tiger-sudo894/NVIDIA-req-limit-proxy/blob/a200efb6d81c66b7f75764d9fe7c7739c74bb47b/nvidia_rate_limit_proxy.py#L132-L149)

## imviren/nvidia-api-rate-limiter

- FastAPI/httpx/Uvicorn와 TLS truststore 또는 certifi를 사용하는 native script다. 실제 `python nvidia_proxy.py` CLI 기본값은 **25 RPM·동시 1개·완료 후 1.67초 간격**이다. 파일 전역의 40 RPM과 README 표는 CLI override와 다르다. Docker/WSL은 필수가 아니다. 제공 Windows installer는 관리자 승격과 인증서/클라이언트 설정 변경도 포함하므로 단순 Python 실행과 별개다. installer는 실행하지 않았다. [imports·전역값](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L1-L30), [실제 CLI 기본값](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L662-L687), [stream 완료와 pacing](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L127-L179), [installer 동작](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/initial_setup.bat#L11-L55)
- **RPM 장부는 upstream send 직전이 아니라 성공 header를 받은 뒤 추가된다.** 429·다른 HTTP 오류는 앞에서 반환하므로 같은 장부에 세지 않는다. 전역 sliding window는 있지만 모든 시도의 start RPM을 기록하는 계약은 아니다. `stream_complete_event`와 순차 gate는 긴 stream이 끝나기 전 다음 요청을 막는다. [장부 함수](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L127-L179), [send 경로](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L507-L559), [오류 반환·기록 위치](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L578-L605)
- **README의 “429 최대 5회 재시도”와 현재 코드는 불일치한다.** 현재 경로는 429 body를 반환하고 해당 model을 기본 7,200초 cooldown에 넣는다. 뒤의 같은 model 요청에는 로컬 429/Retry-After를 만들며, 기존 요청 자체의 재시도 loop는 없다. 최초 upstream 429 응답은 원래 header도 그대로 복사하지 않는다. “429는 언제나 모델 quota”라는 코드 주석은 이 repo의 가정이며 NVIDIA 공식 보장으로 채택할 수 없다. [README 기능 주장](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/README.md#L5-L23), [실제 429 반환](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L578-L605), [후속 요청 gate](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L480-L499)
- 성공 응답은 `aiter_raw()`로 chunk를 바로 전달한다. 그러나 다음 요청은 앞 stream 완료와 holdout을 기다린다. context pruning은 **기본 켜짐**, CLI ceiling은 170,000 추정 token이다. 큰 messages 배열을 재작성하므로 단순 proxy와 답변 품질/입력량이 같다고 비교하면 안 된다. 비교 시 `--no-context-pruning`을 명시해야 한다. [stream relay](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L605-L636), [messages 재작성](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L196-L238), [pruning 기본값](https://github.com/imviren/nvidia-api-rate-limiter/blob/45903b86f120f31c61a1d2ea80adc0c9a5fe244c/nvidia_proxy.py#L662-L687)

## 이번 설계에 적용할 판단

1. **새로움의 범위를 좁힌다.** local proxy·OS 비유·fairness·429 retry 자체로 논문 독창성을 주장하지 않는다. 공유 RPM/TPM의 어떤 계약에서, 어떤 원문·stream 보존과 자원 상한을 지키면서, 동일 시도 예산으로 완료량·tail latency를 개선했는지를 입증해야 한다.
2. **비교 전에 의미를 맞춘다.** HiveMind의 per_agent/global, Tiger의 전체 응답 보관, imviren의 1-slot·pruning·2시간 cooldown은 서로 다른 제품 선택이다. 기본 설정끼리의 수치는 해당 선택까지 포함한 결과이며 스케줄러 알고리즘만의 우위가 아니다.
3. **이 자료가 입증하지 않는 것:** 실제 NVIDIA 계정 RPM/TPM 범위, free tier 보장, 다른 PC와 공유된 한도, 각 repo의 실행 신뢰성·Windows 호환·메모리·성능, 우리 제품의 우위·사용자 채택. 두 NVIDIA 이름의 repo는 NVIDIA 공식 조직 repo가 아니며, 체크아웃에 LICENSE 파일과 테스트 파일도 확인되지 않았다. GitHub stars/채택 규모는 이번에 조회하지 않았다.

이번 범위의 직접 검증은 clone SHA/remote/clean 및 인용 파일·행·해시다. 성능 수치는 만들지 않았다.
