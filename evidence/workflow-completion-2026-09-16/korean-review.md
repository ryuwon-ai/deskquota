# 한국어 문구 검토

검토일: 2026-09-16. humanize-korean v1.5 fast monolith 절차를 적용한 읽기 전용 검토다. 현재 상속 모델을 사용했으며 Opus는 사용하지 않았다. README와 보고서 원본은 수정하지 않았다. 아래는 반영할 교정안이며, 사실 검증이나 새 측정 결과가 아니다. 검토 시점에 peer·짧은 프로파일 결과는 추가 예정이므로 해당 결과를 완료형으로 바꾸지 않는다.

## README 한도 안내

첫 문장은 `로컬 게이트웨이가 적용할 한도를 선택하세요.`가 자연스럽다. 표는 다음처럼 최소한으로 다듬는다.

| 한도 선택 | 의미 |
|---|---|
| 숫자 | 최근 60초의 RPM·TPM을 로컬에서 제한 |
| `unknown` | 로컬 한도를 추가하지 않고 제공자에게 맡김. 실제 제공자 한도는 미확인 |
| `unlimited` | 로컬 RPM·TPM 제한을 두지 않겠다는 명시적 선택 |

후속 문장의 `어느 선택에서도`는 `어떤 항목을 선택해도`로 바꾸면 된다. 연속 보충 정책, 불필요한 로컬 대기, 별도 로컬 예산, `unknown`의 개인별 할당량 미보장 설명은 그대로 유지한다.

## README 측정 설명 교정안

Apple M4·32 GiB RAM 환경과 저사양 PC에 대한 유보 문장은 수정할 필요가 없다. 이어지는 두 단락은 다음처럼 다듬을 수 있다.

원본 18건을 **RPM 한도가 연속 보충되는 모의 서버**에서 전후 5쌍 비교했습니다.
기존의 제공자 위임 설정을 선택하자 요청별 완료 시간의 p95가 **38.13초에서 2.51초**로 줄었습니다.
양쪽 모두 **90/90건 완료·upstream 90회**를 유지했습니다. 짧은 입력 그룹의 평균은
**3.76→1.21초**, 도착 간격을 포함한 전체 배치 완료 시간은 **67.59→31.96초**였습니다.
제공자 정책과 다르게 추가된 로컬 60초 제한을 없앤 효과입니다. 새 스케줄러로 얻은
성능이나 제공자 한도 증가를 뜻하지 않습니다. 실제로 최근 60초의 요청 수를 제한하는
서버에서는 모두 완료하기까지 긴 대기가 남았습니다. 별도의 로컬 예산을 지켜야 한다면
숫자 한도를 유지하세요.

기본 실행 파일은 **macOS 10.20 MB / Windows 16.38 MB**이며, 이 Mac에서 측정한 유휴 메모리는
**9.67 MiB**입니다. macOS 기본·BPE 빌드는 **각 456개 검사**, Windows는 **기본 409개·
BPE 관련 236개 검사**를 통과했습니다. 같은 검사가 겹치므로 고유 검사 수로 합산하지 않습니다.
재시도 금지, 설정, 시작·종료, 자동 요약도 문서에 명시한 플랫폼별 범위에서 확인했습니다.

기존 링크는 그대로 둔다.

## 보고서 핵심 교정안

- 서두의 성과 문장은 `연속 보충 한도에서는 원본 18건의 요청별 완료 시간 p95를 38.13초에서 2.51초로 줄였다.`로 쓴다. 기존 설정 비교라는 바로 다음 설명은 유지한다.
- `같은 바이너리의 기존 설정을 비교한5쌍 모두18/18건을 upstream18회로 완료했다.` → `같은 바이너리의 기존 설정을 비교한 5쌍 모두 18/18건을 upstream 18회로 완료했다.`
- `2.51초는 요청별 지연이며 전체18건을2.51초 만에 처리했다는 뜻이 아니다.` → `2.51초는 요청별 완료 시간의 p95이며, 전체 18건을 2.51초 만에 처리했다는 뜻이 아니다.` 전체 배치 완료 시간 31.964초는 그대로 둔다.
- `각 작업 시작에서5초 안에 완료` → `각 작업 시작 후 5초 안에 완료`
- `원래 제출 시각에서125초의 마감과 최대4회 클라이언트 HTTP/실제 제공자 호출 예산을 가진다.` → `원래 제출 시각부터 125초의 마감과 최대 4회의 클라이언트 HTTP/실제 제공자 호출 예산을 둔다.` 마감 연장 금지와 호출 예산의 적용 단위는 그대로 둔다.
- `설정에서 로컬 한도의 의미를 밝힌다.` → `설정에서 로컬 한도의 의미를 설명한다.`
- `기본 Cargo 의존성 그래프에서`·`성공 admission 예산`·`peer managed`·`native local quota` 등 기술적 구분은 단순한 윤문을 위해 다른 개념으로 바꾸지 않는다.

전반적인 띄어쓰기 예: `원본18건` → `원본 18건`, `전후5쌍` → `전후 5쌍`, `로컬60초` → `로컬 60초`, `실행당 측정100건` → `실행당 측정 100건`, `warmup5건` → `warmup 5건`, `기본456 통과` → `기본 456 통과`, `실패0` → `실패 0`, `retry11건` → `retry 11건`, `M4 32GiB` → `M4 32 GiB`. 숫자와 단위 자체는 바꾸지 않는다. 코드·헤더·경로 내부에는 이런 치환을 적용하지 않는다.

## 보존 확인

1. 제안문은 수치·단위·날짜·고유명사와 링크 목적지를 바꾸지 않는다. 의미를 드러내는 띄어쓰기와 표현만 수정한다.
2. 원본을 수정하지 않았으므로 파일 전체 변경률은 산출하지 않았다. 반영 범위는 위 문장과 띄어쓰기로 한정한다.
3. README는 격식체, 보고서는 평서형 리포트 문체를 유지한다.
4. 2.51초는 요청별 p95이고 31.96초는 도착 간격을 포함한 배치 완료 시간이라는 구분을 유지한다.
5. 기존 quota 설정 비교, bucket과 strict rolling의 차이, 단일 진단과 반복 실험의 범위, 실패·취소·마감 초과를 성공 백분위수로 대체하지 않는 원칙을 유지한다.
6. 새 알고리즘·실제 API·저사양 환경·경쟁 제품 전반의 우위를 추가하지 않는다. 새 비유나 과장 표현도 넣지 않는다.
