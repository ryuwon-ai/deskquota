## Confirmed behavior findings

1. **[P1] Reconnect adopts user additions into the created-file deletion hash.** `product/src/config_patch/apply.rs:242-245` sets `pending_created_hash` to every later candidate when the resource was originally created, and `:283-285` promotes it without checking that the current preimage was still wholly owned. `product/src/config_patch/restore.rs:121-136` then deletes matching bytes. Independent counterexample: create absent settings with model `gateway-v1`; user adds `user_added: preserve-me`; reconnect changes model to `gateway-v2`; disconnect deletes the entire file and reports `Restored`, zero preserved files. This violates preservation of a changed created file. Do not broaden whole-file ownership to include user additions. Cover unchanged reconnect and failed/interrupted reconnect as well as user field/comment additions.

2. **[P2] Repeated ancestor/descendant ownership can falsely report complete restoration.** `product/src/config_patch/apply.rs:225-239` checks only exact existing key equality when extending a journal, whereas `mod.rs:validate_patch_shape` rejects overlap only inside one patch. `restore.rs:170-204,219-245` consequently creates overlapping restore edits and marks each restored without checking its final semantic value. Independent counterexample: original `provider.model=original`, `provider.other=keep`; first connect owns `provider.model=gateway`; second owns the whole `provider={model:gateway,other:changed}`. Restore leaves `provider.model=gateway`, returns no conflicts and marks the journal `Restored`. The later ancestor before-image contains the earlier gateway value and overwrites the descendant restoration. Preserve first preownership and one unambiguous logical ownership boundary, or refuse cross-connect overlapping ownership before any client write; do not add a general migration framework.

3. **[P2] A partial apply omits targets after the failing resource.** `product/src/config_patch/apply.rs:87-101` creates resource records incrementally, records the failing patch only, then returns. Independent three-resource transaction with the second client's directory unwritable fails after writing the first. `inspect_journal` reports only two resources, with owned-key counts `[1,0]`; the third reviewed resource is unchanged but entirely absent from inspection. Every reviewed target needs an inspectable planned/never-started outcome with no fabricated ownership or backup for an unwritten target. This is not a request to write subsequent files after failure.

The executable counterexamples are `probe.rs`; results are `probe-result.json`. All three return `spec_pass: false` while the probe process itself exits successfully. Each used synthetic files and the exact held new library; none used real user config or a real client.
